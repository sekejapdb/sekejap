# The format gate

Every 0.19 format step (`docs/core/SUPPORTIVE.md` section 6) is measured
against the released 0.18.5 with the same fixed set of measurements. The rule
is section 5's: each metric of each operation is at most 1.05 times the
0.18.5 value, never averaged across operations, and the stored bytes of
tables that were never altered stay identical.

The harness is `tools/format_gate.py` (Python 3, standard library only). It
runs bench binaries that are already built; it never builds.

Measurements run on the acceptance device, not on the development machine.
The development machine may run the `smoke` size only, to check the wiring.

## What is measured

| # | Operation | Program | Metrics |
|---|---|---|---|
| 1 | point read by key | `two_ways --only eq_indexed_one --pages` | wall time, page accesses |
| 2 | key-only scan | `q6_budget <popsim file> --stage page --passes 2` | ns per row, page accesses and misses per row |
| 3 | filtered scan with projection | `q3_budget` | wall time; allocations, bytes allocated, page accesses per candidate |
| 4 | insert, commit every 256 | `popsim e4`, `battle50k e4` | wall time per row, bytes on disk |
| 5 | insert, update, delete with an index live | `phase2_scalar_bench e4 --pages` | wall time and page accesses per row |
| 6 | late index build | `popsim` and `battle50k` index stages | wall time per row, bytes on disk |
| 7 | edge write, single and batched | `g2_budget --bytes`, `graph_write_budget --bytes` (with and without `--many`) | per-stage time and page accesses, WAL frames, bytes per edge |
| 8 | graph walk, 1 and 2 hops | `hop1_budget --pages` | wall time, page accesses (BFS alone and through the query engine) |
| 9-12 | text, vector (recall@10), spatial, aggregate | `battle50k e4 --heap` cases | median wall time, peak live heap, row count, recall |
| 13 | whole file | `foundation_space` plus the harness's digest | bytes, pages, one digest per keyspace |
| - | reopen at 1, 100 and 10,000 tables | `format_gate_cases reopen` | reopen time; page accesses to open, resolve a table and read a row |
| - | WAL bytes per DDL commit | `format_gate_cases reopen` and `narrow` | WAL bytes and frames of one `CREATE TABLE` commit |
| - | narrow table at 50K rows | `format_gate_cases narrow` | insert time and bytes per row, point read and scan time and page accesses |

`python3 tools/format_gate.py run ...` records, for each case, the program,
its arguments and the metrics of every repetition. Each metric names its unit.

The whole-file digest reads every live leaf cell of a checkpointed `data`
file and groups the cells by their key's first byte (the keyspace). Each group
gets a cell count and a digest that does not depend on cell order, so a page
that split in a different place does not change it. An overflow value counts
by its length and checksum, not by its page number. Row, edge and posting
keyspaces must match 0.18.5 exactly. A keyspace a step changes on purpose
(for example catalog records moving to the Register) can be passed with
`--allow-digest <hex>`. It is then shown as REPORTED, and the step's notes
must say why.

The battle corpus is generated by the harness (the shape of
`bench/tests/battle50k_smoke.rs`, deterministic) unless `--corpus` and
`--queries` name files. Its SHA-256 is recorded, and `compare` fails two
results measured on different corpora.

## Building

Every revision, the 0.18.5 baseline included, is built with the gate's own
copies of the bench programs, so the only difference between baseline and
candidate is the engine. The added options (`--pages`, `--bytes`, `--heap`,
`format_gate_cases`) compile against the v0.18.5 source.

```sh
python3 tools/format_gate.py build-help --rev v0.18.5   # the baseline
python3 tools/format_gate.py build-help --rev <candidate commit>
```

Each prints the commands: a detached worktree at the revision, the gate's
bench sources copied in, `cargo build --release --locked` with the features
`compact-cells,sqlite-balance,keyspace-append,slotref-split`, and the
worktree removed. `SCRATCH` and `GATE_TARGETS` must be directories outside
the repository. `--overlay-rev <rev>` takes the gate sources from a commit
instead of the working tree.

## Running

```sh
G=python3 tools/format_gate.py
$G run --rev v0.18.5  --size 50k --out "$GATE_OUT/a" --bin-dir "$GATE_TARGETS/v0.18.5/release"
$G run --rev v0.18.5b --size 50k --out "$GATE_OUT/b" --bin-dir "$GATE_TARGETS/v0.18.5/release"
$G compare "$GATE_OUT/a/v0.18.5-50k.json" "$GATE_OUT/b/v0.18.5b-50k.json"
```

1. Run the baseline against itself first, as above. If `compare` lists a
   wall-time metric that differs by more than 2%, the device is too noisy for
   that many repetitions: raise `--reps` (default 3) and repeat until the
   baseline passes against itself.
2. Run the candidate at 50K with the same `--reps`, and compare.
3. Only when 50K passes, run baseline and candidate at `--size 1m`.

Each case runs in its own new directory under `--out`. The databases are
deleted after each repetition unless `--keep` is given; logs stay. The run
takes one popsim database into the key-scan and whole-file cases, and the
battle and g2 databases into their whole-file cases.

## Reading the comparison

`compare` prints one row per metric: case, metric and unit, baseline,
candidate, ratio, verdict. It exits non-zero if any row fails.

- Wall time and costs (bytes, allocations, peak heap, WAL bytes): PASS when
  the candidate is at most 1.05 times the baseline. Wall time is the median
  of the repetitions.
- Page accesses and WAL frames: never more than the baseline, with no
  tolerance. Fewer shows as `PASS (fewer)`.
- Digests and row counts: identical.
- Recall: never lower.
- `info` rows (p90, cell counts) are shown and never gated.

A missing or failed case is a FAIL. A FAIL is never averaged away by another
case that improved.
